if (alreadyConfirmed.isPresent()) return PaymentResponse.from(alreadyConfirmed.get());

TossPaymentResponse tossPayment = tossPaymentClient.confirm(request);   // ← PG에 재확인

## 1. 무효화된 결정

### 🔴 ADR-002 — "상류 데이터는 이벤트로 수집한다" (Kafka)

정산 도메인에서 Kafka를 쓰지 않으므로 **전면 무효**입니다. 연쇄로 무너지는 것들:

| 무너진 것 | 위치 | 사유 |
|---|---|---|
| 이벤트 카탈로그 6종 | README 8장 | `OrderPaid` / `OrderRefunded` 구독 구조가 사라짐 |
| Transactional Outbox 필수화 | README 8.2 | 발행할 이벤트가 없음 |
| ACL `inbound/consumer/` 계층 | README 9.3 | Consumer 대신 배치 Reader |
| 의존 관계도의 Kafka 노드 | README 6.1 | 전면 재작성 |
| 정산 반영 시퀀스 | README 7.1 | 실시간 적재 → 배치 적재 |
| **리스크 R-01** (이벤트 유실) | README 13.2 | **소멸** — 유실될 이벤트가 없음 |
| **"충돌 2" 해소 논리** | README 0장 | 전제가 사라져 무의미 |

> ✅ **좋은 소식**: 이 설계에서 가장 컸던 미해소 리스크 R-01이 사라집니다. 배치 Pull은 실패하면 재실행하면 되므로, "조용히 누락되고 발견 못 함"이 구조적으로 발생하지 않습니다.
>
> ⚠️ **단, 형태를 바꿔 재발합니다.** [F4](#f4--주문결제-흐름의-조정-방식-choreography-vs-orchestration)에서 "결제 성공 / 주문 미확정" 건이 생기면 **정산 Pull 대상에서 통째로 빠집니다.** 이벤트 유실이 아니라 상류 상태 누락으로 경로만 바뀐 것입니다. → F4의 **보정 배치**와 [F9](#f9--대사reconciliation-편입--adr-008-개정)의 **대사**가 이 구멍을 닫습니다. R-01은 *소멸*이 아니라 **"대사로 탐지 가능, 정정은 수동"**으로 개정합니다.

### 🔴 ADR-003 — "수수료는 거래 발생 시점에 계산한다"

거래 시점 계산은 **이벤트를 실시간으로 받는다는 전제** 위에 있었습니다. 배치 수집이면 성립하지 않습니다.

- 자동으로 **배치 실행 시점 계산**이 됩니다
- 단, **어느 시점의 정책을 적용할지**는 여전히 선택입니다 → [F2-b](#f2-b-수수료-정책의-기준-시점)
- 기존에 "실무 재조사 필요"로 남겨둔 항목이었으므로, **재조사 부담도 함께 사라집니다**

### 🔴 README 7.4 — "실시간 정산 현황 조회"

D2에서 *"실시간 조회 필요 = 예"*로 답했고 그것이 ADR-002·003의 근거였습니다. 배치 수집이면 **마감 전 데이터가 원장에 없으므로 실시간 조회가 불가능**합니다 → [F2-a](#f2-a-실시간-정산-현황-조회는-철회하는가)에서 확인 필요.

## F1 — 정산 Aggregate의 루트와 경계 ⭐핵심

> 피드백 4번. **이번 재설계에서 가장 중요한 결정**이며, 전술적 설계 문서의 중심이 됩니다.

정산의 핵심 불변식은 [README 3.3](tactical-design.md#2-불변식과-보장-수단)에 7개를 정리해뒀습니다. 그중 **Aggregate 안에 들어와야 코드로 강제되는 것**은 이 둘입니다.

- **I2** — 마감된 주기의 금액은 변경 불가
- **I4** — `net` = 해당 범위의 전표 합계와 항상 일치

**Aggregate 경계를 어디에 긋느냐가 "어떤 불변식을 트랜잭션으로 지킬 수 있는가"를 결정합니다.**

### 선택지

#### A안 — `SettlementTransaction` 루트 (거래 1건 = 1 Aggregate)

```
SettlementTransaction (AR)
 ├─ txId, txType, orderNo, sellerId, cycleDate, status
 └─ entries: List<SettlementEntry>     ← 내부 Entity
      SALE +10,000 / FEE -500
```

| 지킬 수 있는 불변식 | 지킬 수 없는 불변식 |
|---|---|
| I4 (전표 합계 = net) · I3 (멱등) | **I2 (마감 불변)** — 마감은 여러 거래에 걸친 개념이라 Aggregate 밖 |

- **크기**: 아주 작음 (전표 2~4개). 동시성 경합 없음
- **마감 처리**: 배치가 여러 Aggregate를 순회하며 상태를 바꿈 → **마감의 원자성을 응용 계층이 책임**

#### B안 — `Settlement` 루트 (판매자 × 주기 = 1 Aggregate)

```
Settlement (AR)                        ← sellerId + cycleDate
 ├─ status: PENDING → CONFIRMED
 ├─ netAmount: Money                   ← Value Object
 └─ transactions: List<SettlementTransaction>
      └─ entries: List<SettlementEntry>
```

| 지킬 수 있는 불변식 | 대가 |
|---|---|
| **I2 · I4 모두** — `close()` 메서드가 Aggregate 안에서 상태를 잠금 | **크기 위험** — 한 판매자의 하루 거래 전부를 로드 |

- **마감 처리**: `settlement.close()` 한 번으로 불변식이 코드로 강제됨 ← **DDD 관점에서 가장 깔끔**
- **위험**: 거래가 수천 건이면 Aggregate 로딩이 무거워짐. 같은 판매자 동시 적재 시 락 경합

#### C안 — `Settlement` 루트 + 전표는 ID 참조 (Aggregate 2개)

```
Settlement (AR)                SettlementEntry (AR)
 ├─ sellerId, cycleDate         ├─ entryId
 ├─ status                      ├─ settlementId   ← ID로만 참조
 └─ netAmount: Money            └─ amount, feePolicyId
```

- Aggregate 간 참조를 **ID로만** 하는 DDD 정석 규칙을 따름
- `Settlement`은 작게 유지되고 마감 불변식(I2)도 지킴
- **대가**: I4(합계 일치)가 **두 Aggregate에 걸쳐** 결과적 일관성이 됨. 전표 추가 시 `Settlement.netAmount` 갱신이 별도 트랜잭션
- ⚠️ **주의**: 원안에는 `SettlementTransaction`(주문 단위)이 없습니다. **"주문 1건 = 전표 N개" 묶음이 사라집니다.**

#### D안 — 3계층 변형 (C안 + 주문 단위 묶음 복원) ✅ **채택**

```
Settlement (AR)                  SettlementTransaction (AR)
 ├─ sellerId, cycleDate           ├─ txId
 ├─ status: PENDING → CONFIRMED   ├─ settlementId   ← ID로만 참조
 └─ netAmount: Money              ├─ orderNo, txType, sourceEventId
                                  └─ entries: List<SettlementEntry>   ← 내부 Entity
                                       SALE +10,000 / FEE -500
```

C안의 **ID 참조 원칙**은 그대로 두되, 전표를 `Settlement`이 아니라 **`SettlementTransaction` 내부 Entity 컬렉션**으로 둡니다.

| 지킬 수 있는 것 | 대가 |
|---|---|
| **I2** — `Settlement.close()`가 마감 상태를 잠금 | **헤더 합계 I4가 결과적 일관성** — `netAmount` 갱신이 별도 트랜잭션 |
| **I4 (주문 단위)** — `entries` 합 = `tx.net`이 한 트랜잭션에서 강제 | 마감 스텝에 **재계산·검증 책임**이 생김 |
| **I3 (멱등)** — `sourceEventId`가 `SettlementTransaction`에 귀속 | Aggregate 2개 — 피드백 *"하나의 Aggregate"*는 부속 질문 해석으로 처리 |

- **크기**: 양쪽 다 작음. `Settlement`은 헤더뿐, `SettlementTransaction`은 전표 2~4개
- **마감 처리**: `close()` 안에서 전표 총합을 재계산해 `netAmount`에 확정한 뒤 상태 전이 → **어긋남이 마감 시점에 반드시 해소됨**
- **실무 근접도**: 헤더/명세를 분리하고 합계는 마감 때 확정하는 것이 일반적인 정산 원장 구조

### 판단 재료

| | A안 (거래) | B안 (판매자×주기) | C안 (분리) | **D안 (3계층)** |
|---|:---:|:---:|:---:|:---:|
| I2 마감 불변 강제 | ✗ | ✓ | ✓ | **✓** |
| I4 합계 일치 강제 | ✓ | ✓ | ✗ (결과적) | **주문 단위 ✓ / 헤더 △** |
| I3 멱등 귀속 지점 | 거래 AR | 내부 Entity | 전표 AR | **거래 AR** |
| Aggregate 크기 | 작음 | **위험** | 작음 | **작음** |
| 동시성 | 좋음 | 판매자별 경합 | 좋음 | **좋음** |
| **주문 단위 묶음 유지** | ✓ | ✓ | **✗** | **✓** |
| 피드백 *"하나의 Aggregate"* 부합 | ✓ | ✓ | ✗ (2개) | △ (2개 — 부속 질문으로 해석) |
| 구현 난이도 | 낮음 | 중간 | 높음 | **중간** |

### ✍️ 결정란

```
선택: ☐ A안 (거래 루트)   ☐ B안 (판매자×주기 루트)   ☐ C안 (분리)   [v] D안 (3계층 변형)

선택 근거:
  - 주문 1건에 전표 여러 장이 딸리는 구조를 유지하고 싶음 → 주문 단위 묶음(SettlementTransaction)이 필요.
  - 동시에 마감 불변식(I2)은 "판매자 × 주기" 단위 개념이라 별도 루트가 있어야 강제 가능.
  - C안 원안은 주문 단위 묶음이 사라지므로, 전표를 SettlementTransaction 내부에 두는 D안으로 확정.
  - Aggregate 간 참조는 ID로만 (settlementId) — DDD 정석 규칙 준수.

포기하는 불변식 (Aggregate 밖에서 응용 계층이 책임질 것):
  - I4 중 "헤더 합계" 부분. Settlement.netAmount 갱신이 전표 적재와 별도 트랜잭션이므로,
    배치 진행 중에는 netAmount와 전표 총합이 어긋나는 구간이 존재함.
  - 보완: 마감 스텝에서 netAmount를 전표 총합으로 재계산·검증한 뒤 CONFIRMED로 전이 (close() 내부).
    불일치하면 마감을 실패시킴 → 어긋남이 마감 시점에 반드시 해소됨.
  - 주문 단위 I4 (entries 합 = tx.net)는 SettlementTransaction 안에서 트랜잭션으로 강제되므로 유지.

[부속 질문] 피드백의 "하나의 Aggregate를 포함시키자"를 어떻게 해석할 것인가?
  ☐ 정산 컨텍스트에 Aggregate를 정확히 1개만 둔다
  [v] "제대로 된 Aggregate를 최소 하나는 설계하라"는 뜻으로 보고, 필요하면 2개 이상 둔다

[부속 질문] 전표식 원장(ADR-004)은 유지하는가?
  [v] 유지 — SettlementTransaction 내부 Entity 컬렉션으로 표현
  ☐ 단식으로 회귀 — Aggregate를 단순하게
```

## F2 — 상류 데이터 수집 방식 (ADR-002 대체) ⭐핵심

> Kafka가 빠진 자리를 무엇으로 채울 것인가. **경계 규칙이 하나 바뀝니다.**

### ⚠️ 먼저 알아야 할 것 — 경계 규칙 R4가 깨집니다

기존 설계는 이렇게 자랑했습니다.

> *"Settlement은 어떤 서비스도 호출하지 않는 하류 리프다"* (규칙 R4)

이는 **이벤트 구독이었기 때문에** 가능했습니다. 배치가 데이터를 당겨오면 **Settlement → Order 호출이 반드시 생깁니다.** R4를 아래처럼 고쳐 써야 합니다.

```
[기존 R4]  정산은 어떤 상류 서비스도 호출하지 않는다
[개정 R4]  정산은 상류의 공개 API(gRPC)로만 조회하며, 상류 DB에 직접 접근하지 않는다
```

**R2(DB 직접 접근 금지)는 그대로 지켜집니다.** 현행 코드의 `SettlementBatchConfig → OrderRepository` 직접 의존을 없앤다는 목표는 변함없습니다.

### 선택지

#### A안 — 배치가 Order의 gRPC API를 호출 (Pull)

```
[크론] → Settlement 배치 → gRPC → Order.getSettlementTargets(date)
                         → 전표 적재 + 수수료 계산 → 마감
```

| 장점 | 단점 |
|---|---|
| 인프라 최소. 흐름이 단선적이라 디버깅 쉬움 | 배치 시각에 Order로 **대량 조회 부하 집중** |
| 실패 시 재실행하면 됨 (유실 없음) | Order 장애 시 **정산 자체가 중단** |
| 현행 `OrderService.getSettlementCandidates()`를 그대로 살릴 수 있음 | Settlement이 Order API 스펙에 결합 |

#### B안 — Order가 정산 대상을 스테이징에 적재 → Settlement이 조회

```
Order 내부 배치 → settlement_staging 적재
                → Settlement 배치가 gRPC로 조회
```

| 장점 | 단점 |
|---|---|
| 조회 부하가 스테이징 테이블로 분산 | **Order가 "정산 대상"을 판단** → 정산 관심사가 상류로 샘 |
| Order의 트랜잭션 테이블을 직접 훑지 않음 | 배치가 2단계 → 운영 복잡도 |

#### C안 — 파일 인터페이스 (일별 정산 대상 파일)

```
Order 배치 → 일별 파일 생성 → Settlement 배치가 읽어 적재
```

| 장점 | 단점 |
|---|---|
| 실무 정산 시스템에서 오래 쓰인 방식. 대용량에 강함 | 파일 저장소·정합성 검증(건수·합계) 필요 |
| 서비스 간 런타임 결합이 **0** — Order가 떠 있지 않아도 정산 가능 | 재처리·버전 관리가 번거로움 |

### F2-a. 실시간 정산 현황 조회는 철회하는가?

D2에서 *"실시간 조회 필요 = 예"*로 답하셨고, 그것이 Kafka 선택의 근거였습니다. **배치 수집이면 마감 전 데이터가 원장에 없습니다.**

```
[v] 철회한다 — 배치 실행 후 조회만 제공 (가장 단순)
☐ 유지한다 — 배치 주기를 짧게 (시간별 등)해 "준실시간"으로
☐ 유지하되 조회 전용 경로를 따로 둔다 — Settlement이 Order를 실시간 조회해 "예상 금액" 계산 (원장 미적재)
```

> 세 번째는 "확정 금액(원장)"과 "예상 금액(계산)"을 분리하는 실무 패턴이지만, **API가 늘어납니다** (피드백 1의 *"API가 많지 않다"*와 상충).

### F2-b. 수수료 정책의 기준 시점

배치 시점에 계산하더라도, **어느 날짜의 정책을 적용할지**는 선택입니다. 불변식 I5(계산 근거 재현)와 직결됩니다.

```
[v] 거래 발생일 기준 — 1/15 거래는 1/15 정책. 정책 변경이 소급되지 않음
☐ 배치 실행일 기준 — 1/16 배치는 1/16 정책. 구현은 단순하나 소급 적용됨
```

> 어느 쪽이든 **적용한 `feePolicyId`를 전표에 기록**하는 것은 동일합니다 (I5).

### ✍️ 결정란

```
수집 방식: [v] A안 (gRPC Pull)   ☐ B안 (스테이징)   ☐ C안 (파일)

선택 근거:
  - 내부 시스템이다보니, 빠른 처리를 도와주는 A안을 선택

F2-a 실시간 조회:  [v] 철회   ☐ 준실시간   ☐ 예상 금액 별도 경로
F2-b 정책 기준일:  [v] 거래 발생일   ☐ 배치 실행일

개정 R4 문구 승인: [v] 승인   ☐ 다르게 표현 (________)
```

## F4 — 주문·결제 흐름의 조정 방식 (Choreography vs Orchestration)

> 피드백 3번. **Kafka가 빠지면 Choreography(이벤트 기반 자율 반응)가 사실상 불가능**해집니다. 그러면 무엇이 흐름을 조정하는가?

### 먼저 정리 — 두 방식의 차이

| | Choreography | Orchestration |
|---|---|---|
| 조정 주체 | 없음. 각 서비스가 이벤트에 **자율 반응** | 중앙 조정자가 **순서대로 지시** |
| 필요 인프라 | 메시지 브로커 | 없음 (동기 호출로 가능) |
| 흐름 추적 | 어려움 — 전체 흐름이 코드 어디에도 없음 | 쉬움 — 조정자 코드에 흐름이 명시 |
| 결합도 | 낮음 | 조정자가 참여자를 앎 |

**Kafka를 쓰지 않기로 했으므로 Choreography는 선택지에서 빠집니다.** 남은 질문은 *"누가 조정자인가"*입니다.

### 선택지

#### A안 — 프론트엔드가 조정 (현행 코드와 동일)

```
프론트 → PG 결제창 → paymentKey 획득
프론트 → Payment.confirm(paymentKey)   → PG 확인 → 저장
프론트 → Order.confirm(orderNo)        → 주문 PAID 전이
```

| 장점 | 단점 |
|---|---|
| **현행 코드 그대로.** 추가 작업 거의 없음 | ⚠️ 프론트가 중간에 끊기면 **결제는 됐는데 주문은 미확정** |
| 서버 간 호출이 없어 결합 최소 | 비즈니스 흐름이 프론트에 샘 → 도메인 로직 누수 |

#### B안 — Payment가 Order를 호출 (gRPC)

```
프론트 → Payment.confirm(paymentKey) → PG 확인 → 저장
                                     → gRPC → Order.markPaid(orderNo)
```

| 장점 | 단점 |
|---|---|
| 결제 승인과 주문 확정이 **서버에서 이어짐** | Payment가 Order를 앎 → **결제가 주문 도메인에 의존** |
| 프론트 이탈에 강함 | Order 장애 시 결제만 성공하고 주문이 남음 (보상 필요) |

#### C안 — Order가 오케스트레이터 (진짜 Orchestration)

```
프론트 → PG 결제창 → paymentKey 획득
프론트 → Order.confirmPayment(orderNo, paymentKey)
           → gRPC → Payment.confirm(paymentKey)  → PG 확인 → 저장
           → 주문 PAID 전이 (같은 유스케이스 안에서)
```

| 장점 | 단점 |
|---|---|
| **흐름이 Order 한 곳에 명시됨** — 추적·디버깅 쉬움 | 피드백 6번(*"프론트가 결과를 Payment에 전달"*)과 **경로가 달라짐** — 프론트가 Order를 거침 |
| 주문 상태 전이의 주인이 Order로 일관됨 | Order → Payment 의존 추가 |

> ⚠️ **피드백 6번과의 정합성을 확인해야 합니다.** 피드백은 *"프론트가 PG 호출 후 결과를 Payment에 전달하고, Payment가 PG에 확인 후 저장"*까지만 말합니다. **주문 상태를 누가 언제 바꾸는지는 언급이 없습니다.** A·B안은 피드백 경로를 그대로 따르고, C안은 프론트가 Order를 경유하도록 바꿉니다.

### ✍️ 결정란

```
선택: ☐ A안 (프론트 조정)   [v] B안 (Payment → Order)   ☐ C안 (Order 오케스트레이션)

선택 근거:
  -

"결제 성공 / 주문 미확정" 상태를 어떻게 다룰 것인가?
  [v] 보정 배치로 주기적 정합화    [] 프론트 재시도에 맡김    [] 이번 범위에서 다루지 않음

이 흐름을 문서에 Saga로 부를 것인가?
  [v] Saga라 부르지 않고 "유스케이스 흐름"으로 서술 (피드백 2 반영)
  ☐ Saga 용어 유지
```

## F5 — gRPC 적용 범위와 proto 관리

> 피드백 9번. 무엇을 gRPC로 하고, **계약(proto)을 누가 소유하는가**.

### F5-a. 적용 범위

```
☐ 모든 내부 서비스 간 호출을 gRPC로
☐ 정산 ↔ 주문 구간만 gRPC, 나머지는 REST
[v] 외부(클라이언트) API는 REST 유지 + 내부만 gRPC   ← 통상 조합
```

### F5-b. proto 파일의 소유

DDD 관점에서 이건 **Context Map 관계 유형**을 정하는 일입니다.

| 선택지 | DDD 패턴 | 결과 |
|---|---|---|
| **공용 `common-proto` 모듈** | **Shared Kernel** | 편하지만 **모든 서비스가 한 모듈에 결합**. 변경 시 전체 영향 |
| **제공자가 소유, 소비자가 참조** | **Open Host Service + Published Language** | 결합 낮음. Order가 자기 proto를 공개하고 Settlement이 가져다 씀 |
| 소비자가 자기 버전 유지 | **ACL 강화** | 결합 최저, 중복 최다 |

> 기존 설계는 `common-event` 공용 모듈을 두면서 *"공유 모듈이 새로운 결합점이 되는 것을 방지하기 위해 DTO만 둔다"*고 못 박았습니다. **proto도 같은 고민이 필요합니다.**

### ✍️ 결정란

```
F5-a 적용 범위: ☐ 전체 내부   ☐ 정산↔주문만   [v] 내부 gRPC + 외부 REST

F5-b proto 소유: ☐ common-proto 공용 (Shared Kernel)
                 [v] 제공자 소유 (Open Host Service)
                 ☐ 소비자별 유지 (ACL)

## F7 — 서비스 분할 규모 재확인

> *"너무 크지 않은 규모로 다시 설계"* 요구에 따라 ADR-001·007을 다시 봅니다. 현재 설계는 **서비스 6개 + 게이트웨이**입니다.

### 선택지

| | 구성 | 서비스 수 |
|---|---|---|
| **A안** | 현행 유지 — Settlement, Order, Payment, Product, Member, Payout | 6 |
| **B안** | Member 제외 — Order가 `buyerId`/`sellerId`만 보유 | 5 |
| **C안** | Settlement · Order · Payment · Product 4개로 축소 (Member·Payout 제외) | 4 |
| **D안** | Settlement · Order · Payment 3개 (Product를 Order에 흡수) | 3 |
| **E안** ✅ | **A안 변형 — Payout 제외** (Settlement · Order · Payment · Product · Member) | **5** |

### 판단 재료

- **Member는 이미 최소 구성**입니다. Q5에서 계좌를 지급 대행사가 보유하기로 해 `seller_account`도 없고, 남은 건 신원뿐입니다 → **제거 부담이 작습니다**
- **Payout은 이미 ⏸ 경계만 정의**이므로 서비스 수에 실질 부담이 없습니다
- **Product는 주문의 재고·가격 검증에 필요**하지만, 현행 코드는 주문 시 재고를 전혀 건드리지 않습니다 (README 2.2 ④)
- 피드백 1번의 *"API가 많지 않다"*는 정산에 대한 말이지만, **전체 규모 감각의 신호**로 읽을 수 있습니다

### ✍️ 결정란

```
선택: ☐ A안 (6개)   ☐ B안 (5개)   ☐ C안 (4개)   ☐ D안 (3개)   [v] E안 (A안 변형 · Payout 제외 · 5개)

ADR-001 (정산 코어 / 지급 2분할) 유지하는가?
  ☐ 유지 — 경계만 정의한 상태이므로 부담 없음
  [v] 철회 — 정산 단일 서비스로 통합

근거:
  - 기존 챌린지 코드의 방향성을 잃고 싶지 않아 Member는 남김 (인증·신원은 어차피 필요).
  - Payout은 범위 B라 서비스 목록에서 제외 → ADR-001 철회와 같은 결정.
  - 단, 대사(F9)는 편입하므로 "지급 대사"가 아닌 "매출 대사" 범위임에 유의.
```

## F9 — 대사(Reconciliation) 편입 — ADR-008 개정

> 기존 ADR-008은 대사를 **범위 B로 이연**했습니다. 이 결정을 뒤집어 **범위 A에 편입**합니다.

### 왜 지금 넣는가

이 설계에는 **누락을 탐지할 수단이 없다**는 구멍이 있었습니다. 두 경로로 열립니다.

| 경로 | 내용 |
|---|---|
| **F4** | "결제 성공 / 주문 미확정" 건이 Order에 PAID로 안 남음 → **정산 Pull 대상에서 제외** |
| **F2** | gRPC Pull이 부분 실패하거나 페이징 중 누락되면 조용히 빠짐 |

보정 배치(F4)는 **주문·결제 사이**를 맞출 뿐, **우리 원장이 PG의 실제 정산 내역과 맞는지**는 아무도 검증하지 않습니다. 대사가 그 자리입니다.

### 상대편 원장이 실제로 존재합니다 — 토스페이먼츠 정산 조회 API

대사의 본질은 **독립적으로 만들어진 두 원장을 맞춰보는 것**입니다. 자체 목업이 아니라 **진짜 PG 데이터**를 상대편으로 쓸 수 있습니다.

`GET /v1/settlements?startDate=&endDate=&dateType=soldDate|paidOutDate`

| 응답 필드 | 우리 원장에서 대조할 대상 |
|---|---|
| `paymentKey` · `orderId` | 매칭 키 — `SettlementTransaction.orderNo` |
| `amount` | **SALE 전표** 금액 |
| `fees[].fee` · `vat` · `supplyAmount` | **FEE 전표** 금액 (PG 수수료) |
| `payOutAmount` | 결제액 − 수수료 = **`tx.net`** |
| `soldDate` | 정산 매출일 — 우리 `cycleDate`와 대조 |
| `paidOutDate` | 정산 지급일 (지급이 범위 밖이라 **참고만**) |

> `GET /v1/transactions`(거래 조회)도 있습니다. **승인과 취소가 각각 다른 `transactionKey`로 분리**되므로, 환불 역분개(ADR-005) 검증에 쓸 수 있습니다.

### ⚠️ 이 설계에서 가장 까다로운 지점 — 기준일이 어긋납니다

토스 문서는 `soldDate` · `paidOutDate`가 **상점의 정산 주기·기준일에 따라 달라진다**고 명시합니다. 우리는 **고정 D+1**(ADR-006)입니다.

```
우리 원장 :  cycleDate = 거래 발생일 (D)        ← F2-b "거래 발생일 기준"
PG 정산   :  soldDate  = 토스 정산 주기에 따름  ← 우리와 다를 수 있음
```

**같은 거래가 서로 다른 주기에 잡힙니다.** 날짜로 단순 대조하면 전건 불일치가 납니다. 실무 대사가 어려운 이유가 정확히 이것이고, **축소판에 담기 가장 좋은 소재**이기도 합니다.

### 대사 불일치 유형 (4종)

| 유형 | 정의 | 의미 |
|---|---|---|
| **MISSING** | PG엔 있는데 우리 원장에 없음 | **정산 누락** — 판매자 미지급. R-01이 실현된 상태 |
| **ORPHAN** | 우리 원장엔 있는데 PG에 없음 | 과다 계상 — 취소 반영 누락 등 |
| **AMOUNT_MISMATCH** | 양쪽 다 있으나 금액 상이 | 수수료율·절사 규칙 오적용 (I5 재현성 검증에 직결) |
| **CYCLE_MISMATCH** | 금액은 같으나 **주기(날짜)가 다름** | 정산 오류 아님 — PG와 우리 주기 차이. **결정 ①에 따라 별도 기록** |

> **`CYCLE_MISMATCH`는 결정 ①(±N일 확장 매칭)의 산물입니다.** 금액이 맞는데 날짜만 다른 건을 `MISSING` + `ORPHAN` 한 쌍으로 잘못 세지 않기 위해 분리합니다. **알람 대상이 아니라 관측 대상**입니다.

### 탐지까지만 — 자동 수정은 하지 않습니다

실무 대사도 **탐지와 정정을 분리**합니다. 자동 정정은 잘못된 대사 로직이 원장을 오염시키기 때문입니다.

- 결과를 `reconciliation_result`에 기록
  (`type`, `orderNo`, `paymentKey`, `ledgerAmount`, `pgAmount`, `diff`, `ledgerCycleDate`, `pgSoldDate`, `detectedAt`, `status`)
- ⚠️ **`status` + 매칭 키 UNIQUE가 필요합니다.** 결정 ①이 조회 구간을 ±N일로 넓히므로 **같은 거래를 여러 날 배치가 중복으로 집습니다.**
  `paymentKey` 기준으로 이미 `MATCHED` 처리된 건은 재기록하지 않아야 합니다 (대사 배치도 멱등해야 함 — ADR-010 전제와 동일)
- 정정은 사람이 **조정 전표**로 — ADR-005(역분개) · ADR-011(승인 절차 없음) · ADR-015(역할 인가)와 그대로 이어짐
- 원장은 여전히 **append-only**(I1) — 대사가 I1을 깨지 않음

### 선택지 — 대사 범위

| | 범위 | 비용 |
|---|---|---|
| **A안** ✅ | **매출 대사만** — PG 정산 내역 ↔ 확정 원장 대조, 탐지까지 | 배치 스텝 1 · 테이블 1 · 클라이언트 메서드 1 |
| B안 | 매출 대사 + 자동 조정 전표 발행 | 정정 로직 추가 — 오염 위험 |
| C안 | 지급 대사까지 (Payout 필요) | **범위 B** — F7에서 Payout 제외했으므로 불가 |

> **지급이 범위 밖이므로 "지급 대사"가 아니라 "매출 대사"입니다.** 문서에 반드시 구분해 적어야 합니다.

### ✍️ 결정란

```
대사 편입:  [v] 편입한다 (ADR-008 개정)   ☐ 범위 B로 유지

범위:  [v] A안 (매출 대사 · 탐지까지)   ☐ B안 (+자동 조정)   ☐ C안 (지급 대사 — 범위 밖)

선택 근거:
  - 정산 시스템의 신뢰성 축이 대사임. 없으면 "누락을 탐지할 수 없는 정산"이 됨.
  - 토스 정산 조회 API가 상대편 원장을 실제로 제공하므로 목업 없이 성립.
  - 비용이 작음 — TossPaymentClient 메서드 추가 + 배치 스텝 1개 + 결과 테이블 1개.

[결정 필요 ①] 기준일 어긋남을 어떻게 맞출 것인가?
  ☐ paymentKey / orderId 로만 매칭하고 날짜는 대조 대상에서 제외 (가장 단순)
  [] PG soldDate 기준으로 우리 원장을 역조회해 맞춤
  [v] 조회 구간을 ±N일로 넓혀 매칭 후, 주기 차이는 별도 유형으로 기록
      → N = 3 일  (미정. PG 정산 주기 확인 후 확정 — 주말·공휴일 이월을 덮으려면 최소 3~4일 필요)
      → 주기 차이 기록용 유형: CYCLE_MISMATCH (위 표에 추가함)

[결정 필요 ②] 불일치 허용 오차를 둘 것인가? (원 단위 절사·반올림 차)
  [v] 0원 — 1원이라도 다르면 불일치      ☐ ±N원 허용 (N = ____)

  ⚠️ 0원을 택했으므로 전제가 따라붙습니다 — 우리 수수료 계산의 절사·반올림 규칙이
     PG와 동일해야 합니다. 토스 수수료는 supplyAmount(공급가액) + vat(부가세) 구조이고
     부가세에 원 단위 절사가 들어갑니다. 요율만 맞추고 절사 규칙이 다르면
     정상 거래가 전건 AMOUNT_MISMATCH로 잡힙니다.
  [확인 필요] PG 수수료 절사 규칙 확인 후 feePolicy 계산식에 반영:  ☐ 확인함   ☐ 미확인
  → 확인 전까지는 대사 결과를 "관측만" 하고 알람은 끄는 편이 안전합니다.

[결정 필요 ③] 대사 배치 실행 시각 (마감 03:00 이후)
  06:00 단, PG 정산 데이터 확정 시점에 따라 달라질 예정        ※ PG 정산 데이터 확정 시점을 확인해야 함

  ⚠️ 시각과 별개로 "대사 대상일"이 아직 없습니다 — 둘은 다른 값입니다.
     실행 시각 06:00 / 대상일 = D-3 일치
     토스 soldDate는 상점 정산 주기에 따라 채워지므로, 당일 06:00에 D-1을 대사하면
     PG 쪽에 아직 데이터가 없어 전건 MISSING이 날 수 있습니다.
     → 대상일 오프셋을 PG 정산 확정 시점보다 뒤로 잡아야 합니다.

# 권장 결정 순서

```
F8 (문서 구조)  →  F7 (서비스 규모)  →  F2 (수집 방식)  →  F1 (Aggregate)  →  F4 (조정 방식)
   어디에 쓸지       무엇을 만들지        어떻게 받을지       어떻게 모델링할지     흐름을 누가 잡을지
                                              ↓
                                   F3 (크론) · F5 (gRPC) · F6 (Kafka)  →  F9 (대사)
                                        세부 구현 방식                     마지막에 검증 축
```

**F2 → F1 순서가 중요합니다.** 수집 방식이 배치로 확정돼야 Aggregate의 생성 시점(*"언제 전표가 만들어지는가"*)이 정해지고, 그래야 Aggregate 경계를 제대로 그을 수 있습니다.

### 결정 간 연동

| 연동 | 내용 |
|---|---|
| **F2 → F1** | 배치 적재면 Aggregate가 **배치 트랜잭션 단위로 생성**됨 → 크기 산정에 직결 |
| **F2 → F2-a** | 수집이 배치면 실시간 조회가 불가 → 요구사항 철회 여부 확인 필요 |
| **F1 → ADR-004** | Aggregate를 작게 가져가면 전표식 유지가 쉽고, 크게 가져가면 부담 |
| **F7 → F4** | 서비스를 줄이면(D안) Product 호출이 사라져 조정 흐름이 단순해짐 |
| **F5 → F2** | proto 소유 방식이 정산·주문 간 결합도를 좌우 |
| **F6 → F8** | Kafka 전면 제거면 전략 문서에서 메시징 절을 통째로 삭제 |
| **F4 → F9** | 보정 배치는 주문↔결제만 맞춤. **PG와의 정합은 대사만 검증** — 둘은 대체재가 아님 |
| **F9 → ADR-008** | 대사 편입으로 범위 A 정의가 바뀜 → **ADR-008 개정 필수** |
| **F9 → R-01** | 리스크가 *소멸*이 아니라 **"대사로 탐지 가능, 정정은 수동"**으로 개정됨 |
| **F7 → F9** | Payout 제외이므로 대사는 **매출 대사**까지. 지급 대사는 범위 B |
| **F2-b → F9** | "거래 발생일 기준"과 PG `soldDate`가 어긋남 → 매칭 키 설계에 직결 |
