# ADR-024. 정산 설계에서 Kafka를 전면 제거한다

> 🟢 **승인 (Accepted)** — F6 A안 · [ADR-002](0002-이벤트-수집-kafka.md) 폐기의 직접 근거

---

- **상태**: 승인 · **관련**: [ADR-017](0017-배치-grpc-pull-수집.md), [ADR-022](0022-payment-order-호출-보정배치.md)
- **맥락**: 피드백 1번 — *"크론잡을 쓰지, 정산 도메인에서 카프카를 쓰지 않는다."* 피드백 5번은 조건부 허용을 덧붙였다 — *"이력은 Kafka로 남겨도 된다. 단 꼭 쌓여야 하면 내부에 쌓아야 한다."* 전면 제거(A) / 유실 허용분만 유지(B) / 이연(C)
- **결정**: **안 A — 전면 제거.** 1주차 범위에서 Kafka를 쓰지 않는다
- **근거**
  - 피드백 5번의 기준을 정산 데이터에 적용하면 **Kafka에 남길 것이 사실상 없다**

    | 데이터 | 유실 허용? | 저장 위치 |
    |---|:---:|---|
    | 정산 원장 (전표·거래) | ❌ **절대 불가** | 내부 DB — 이론의 여지 없음 |
    | 마감 결과 | ❌ 불가 | 내부 DB |
    | 조정 이력 (`issued_by`) | ❌ 불가 (감사 대상) | 내부 DB |
    | 정산 조회 로그 | ✅ 허용 | Kafka 가능 — **그런데 이번 범위에 소비자가 없다** |

  - **돈을 다루는 도메인에서 "못 받은 걸 모르는" 전송은 쓸 수 없다.** 배치는 "안 돌았다"가 관측되지만 이벤트 유실은 조용하다
  - 유실 허용 데이터만 남기자고 브로커를 세우면 **운영 부담 대비 얻는 것이 없다**
- **포기한 것**
  - 챌린지 후반 주차의 Kafka 학습 연속성 — **후반 주차에 별도로 도입한다.** 정산 원장 경로가 아니라 분석·이력 경로로 붙이는 편이 도메인에도 맞다
  - 서비스 간 비동기 완충이 사라져 [ADR-022](0022-payment-order-호출-보정배치.md)의 동기 호출 실패가 직접 드러난다 → 보정 배치로 대응
- **연쇄 삭제**: 이벤트 카탈로그 6종, Transactional Outbox 절, ACL의 `inbound/consumer/` 계층, 의존 관계도의 Kafka 노드가 모두 사라진다
- **⚠️ 리스크 R-01은 삭제되지 않는다**: *"이벤트 유실로 정산 누락"*은 사라지지만, [ADR-022](0022-payment-order-호출-보정배치.md)의 "주문 미확정" 경로로 **형태를 바꿔 재발한다.** [ADR-025](0025-대사-범위-편입.md)의 대사가 탐지 수단이다
- **재검토 조건**: 후반 주차 Kafka 도입 시 — 단, 정산 원장 경로에는 넣지 않는다
