# ADR-022. 결제 승인 후 Payment가 Order를 호출하고, 어긋남은 보정 배치로 맞춘다

> 🟢 **승인 (Accepted)** — F4 B안

---

- **상태**: 승인 · **관련**: [ADR-023](0023-내부-grpc-외부-rest-proto-소유.md), [ADR-025](0025-대사-범위-편입.md), [ADR-017](0017-배치-grpc-pull-수집.md)
- **맥락**: Kafka를 쓰지 않으므로([ADR-024](0024-kafka-전면-제거.md)) **Choreography는 선택지에서 빠진다.** 남은 질문은 *누가 주문·결제 흐름을 조정하는가*다. 프론트 조정(A) / Payment → Order(B) / Order 오케스트레이션(C)
- **결정**: **안 B.** 프론트가 `paymentKey`를 Payment에 넘기고, **Payment가 PG 확인 후 저장한 뒤 gRPC로 Order를 확정**시킨다

```
프론트 → PG 결제창 → paymentKey 획득
프론트 → Payment.confirm(paymentKey) → PG에 재확인 → 저장
                                     → gRPC → Order.markPaid(orderNo)
```

- **근거**
  - **현행 코드의 결제 경로를 그대로 지킨다** — 프론트가 PG를 호출하고 결과를 Payment에 전달, Payment가 PG에 재확인 후 저장하는 흐름은 이미 구현돼 있다
  - 결제 승인과 주문 확정이 **서버에서 이어진다.** 프론트가 중간에 이탈해도 주문이 확정된다
  - C안은 프론트가 Order를 경유하도록 경로를 바꿔야 해서, 이미 맞게 구현된 부분을 건드린다
- **용어**: 이 흐름을 문서에서 **Saga라 부르지 않는다.** 보상 트랜잭션을 갖춘 분산 트랜잭션 패턴이 아니라 **유스케이스 흐름**이며, DDD 관점의 서술을 유지한다
- **포기한 것 — 그리고 그 대응**
  - Payment가 Order를 알게 된다. 결제가 주문 도메인에 의존한다
  - **Order 장애 시 "결제 성공 / 주문 미확정"이 남는다.** 이 상태는 정산에 직접적이다 — 정산 배치는 Order를 Pull하므로([ADR-017](0017-배치-grpc-pull-수집.md)) **주문이 PAID가 아니면 정산 대상에서 통째로 빠진다.** 판매자 미지급이다
  - **대응: 보정 배치.** "결제는 DONE인데 주문이 PAID가 아닌" 건을 주기적으로 스윕해 정합화한다. [ADR-021](0021-k8s-cronjob-shedlock.md)의 CronJob 인프라에 스텝 하나를 추가하는 비용이다
  - **보정 배치는 주문↔결제 사이만 맞춘다.** 우리 원장이 PG의 실제 정산 내역과 맞는지는 [ADR-025](0025-대사-범위-편입.md)의 대사만 검증한다. **둘은 대체재가 아니다**
- **재검토 조건**: 보정 배치로도 남는 미확정 건이 관측될 때
