# ADR-025. 대사(Reconciliation)를 범위 A에 편입한다 — 매출 대사 · 탐지까지

> 🟢 **승인 (Accepted)** — F9 · [ADR-008](0008-이번-범위.md)을 개정

---

- **상태**: 승인 · **관련**: [ADR-008](0008-이번-범위.md), [ADR-018](0018-배치시점-계산-거래일-정책.md), [ADR-020](0020-서비스-5개-payout-제외.md), [ADR-022](0022-payment-order-호출-보정배치.md)
- **맥락**: [ADR-008](0008-이번-범위.md)은 대사를 범위 B로 이연했다. 그 결과 이 설계에는 **누락을 탐지할 수단이 없다**는 구멍이 있었다

  | 경로 | 내용 |
  |---|---|
  | [ADR-022](0022-payment-order-호출-보정배치.md) | "결제 성공 / 주문 미확정" 건이 Order에 PAID로 안 남음 → **정산 Pull 대상에서 제외** |
  | [ADR-017](0017-배치-grpc-pull-수집.md) | gRPC Pull이 부분 실패하거나 페이징 중 누락되면 조용히 빠짐 |

  보정 배치는 **주문·결제 사이**만 맞춘다. **우리 원장이 PG의 실제 정산 내역과 맞는지**는 아무도 검증하지 않았다

- **결정**: **대사를 범위 A에 편입한다.** 단 **매출 대사**까지이며, **탐지까지만** 하고 자동 정정은 하지 않는다

### 상대편 원장 — 토스페이먼츠 정산 조회 API

대사의 본질은 **독립적으로 만들어진 두 원장을 맞춰보는 것**이다. 목업이 아니라 **실제 PG 데이터**를 상대편으로 쓸 수 있다.

`GET /v1/settlements?startDate=&endDate=&dateType=soldDate|paidOutDate`

| 응답 필드 | 우리 원장에서 대조할 대상 |
|---|---|
| `paymentKey` · `orderId` | 매칭 키 — `SettlementTransaction.orderNo` |
| `amount` | **SALE 전표** 금액 |
| `fees[].fee` · `vat` · `supplyAmount` | **FEE 전표** 금액 (PG 수수료) |
| `payOutAmount` | 결제액 − 수수료 = **`tx.net`** |
| `soldDate` | 정산 매출일 — 우리 `cycleDate`와 대조 |
| `paidOutDate` | 정산 지급일 — 지급이 범위 밖이라 **참고만** |

> `GET /v1/transactions`(거래 조회)는 **승인과 취소가 각각 다른 `transactionKey`로 분리**되므로, 환불 역분개([ADR-005](0005-역분개-전표.md)) 검증에 쓸 수 있다.

### ⚠️ 기준일이 어긋난다 — 이 설계에서 가장 까다로운 지점

토스 문서는 `soldDate` · `paidOutDate`가 **상점의 정산 주기·기준일에 따라 달라진다**고 명시한다. 우리는 **고정 D+1**([ADR-006](0006-정산주기-d1-정책소유.md))이다.

```
우리 원장 :  cycleDate = 거래 발생일 (D)        ← ADR-018 "거래 발생일 기준"
PG 정산   :  soldDate  = 토스 정산 주기에 따름  ← 우리와 다를 수 있음
```

**같은 거래가 서로 다른 주기에 잡힌다.** 날짜로 단순 대조하면 전건 불일치가 난다.

- **해소**: 조회 구간을 **±3일**로 넓혀 매칭하고, 금액은 맞는데 날짜만 다른 건은 `CYCLE_MISMATCH`로 **따로 기록**한다. 주말·공휴일 이월을 덮으려면 최소 3~4일이 필요하다

### 불일치 유형 (4종)

| 유형 | 정의 | 의미 |
|---|---|---|
| **MISSING** | PG엔 있는데 우리 원장에 없음 | **정산 누락** — 판매자 미지급. R-01이 실현된 상태 |
| **ORPHAN** | 우리 원장엔 있는데 PG에 없음 | 과다 계상 — 취소 반영 누락 등 |
| **AMOUNT_MISMATCH** | 양쪽 다 있으나 금액 상이 | 수수료율·절사 규칙 오적용 ([I5](../tactical-design.md#2-불변식과-보장-수단) 재현성 검증에 직결) |
| **CYCLE_MISMATCH** | 금액은 같으나 **주기(날짜)가 다름** | 정산 오류 아님 — PG와 우리 주기 차이. **알람 대상이 아니라 관측 대상** |

> `CYCLE_MISMATCH`가 없으면 주기만 다른 정상 건이 `MISSING` + `ORPHAN` **한 쌍으로 이중 계상**된다.

### 허용 오차 — 0원

**1원이라도 다르면 불일치**로 잡는다.

- **전제**: 우리 수수료 계산의 **절사·반올림 규칙이 PG와 동일해야 한다.** 토스 수수료는 `supplyAmount`(공급가액) + `vat`(부가세) 구조이고 부가세에 원 단위 절사가 들어간다. 요율만 맞추고 절사가 다르면 **정상 거래가 전건 `AMOUNT_MISMATCH`로 잡힌다**
- **선행 작업**: PG 수수료 절사 규칙을 확인해 `feePolicy` 계산식에 반영 ([ADR-018](0018-배치시점-계산-거래일-정책.md))
- **그 전까지**: 대사 결과를 **관측만** 하고 알람은 끈다
- **근거**: 실무 정산도 허용 오차로 덮기보다 **규칙을 맞추는 쪽**을 먼저 잡는다. 오차를 열어두면 진짜 불일치가 그 안에 숨는다

### 탐지까지만 — 자동 정정하지 않는다

실무 대사도 **탐지와 정정을 분리**한다. 잘못된 대사 로직이 원장을 오염시키기 때문이다.

- 결과를 `reconciliation_result`에 기록
  (`type`, `orderNo`, `paymentKey`, `ledgerAmount`, `pgAmount`, `diff`, `ledgerCycleDate`, `pgSoldDate`, `detectedAt`, `status`)
- **`status` + `paymentKey` UNIQUE가 필요하다.** ±3일 확장 조회는 **같은 거래를 여러 날 배치가 중복으로 집는다.** 이미 `MATCHED`인 건은 재기록하지 않는다 — **대사 배치도 멱등해야 한다**
- 정정은 사람이 **조정 전표**로 — [ADR-005](0005-역분개-전표.md) · [ADR-011](0011-조정전표-승인절차-없음.md) · [ADR-015](0015-조정전표-역할-인가.md)와 그대로 이어진다
- 원장은 여전히 **append-only**(I1) — 대사가 I1을 깨지 않는다

### 실행

| 항목 | 값 |
|---|---|
| 실행 시각 | **매일 06:00** (마감 03:00 이후) |
| 대사 대상일 | **D-3** |
| 조회 구간 | 대상일 **±3일** |

> **대상일을 D-1이 아니라 D-3으로 둔 이유**: 토스 `soldDate`는 상점 정산 주기에 따라 채워지므로, 당일 06:00에 D-1을 대사하면 **PG 쪽에 아직 데이터가 없어 전건 `MISSING`**이 난다. 오프셋을 PG 정산 확정 시점보다 뒤로 잡아야 한다.

- **포기한 것**
  - 범위 A가 커진다 — 배치 스텝 1 · 테이블 1 · 클라이언트 메서드 1
  - **지급 대사는 못 한다.** Payout이 범위 밖이므로([ADR-020](0020-서비스-5개-payout-제외.md)) *"실제 송금액이 확정 정산액과 같은가"*(I6)는 검증되지 않는다
  - 불일치를 찾아도 **자동으로 고쳐지지 않는다.** 운영자 개입이 전제다
- **재검토 조건**: PG 절사 규칙 확인 후 — 0원 오차가 실제로 성립하는지 재평가. 지급 착수 시 — 지급 대사 추가
