# ADR-017. 상류 데이터는 배치가 gRPC로 당겨온다

> 🟢 **승인 (Accepted)** — F2 A안 · [ADR-002](0002-이벤트-수집-kafka.md)를 대체

---

- **상태**: 승인 · **관련**: [ADR-021](0021-k8s-cronjob-shedlock.md), [ADR-023](0023-내부-grpc-외부-rest-proto-소유.md), [ADR-024](0024-kafka-전면-제거.md)
- **맥락**: 정산 도메인에서 Kafka를 쓰지 않기로 하면서([ADR-024](0024-kafka-전면-제거.md)) 이벤트 구독이 사라졌다. 상류(Order) 데이터를 무엇으로 받을 것인가. 배치 Pull(A) / 상류 스테이징 적재(B) / 파일 인터페이스(C)를 검토
- **결정**: **안 A — 정산 배치가 Order의 gRPC API를 호출해 당겨온다**

```
[CronJob] → Settlement 배치 → gRPC → Order.getSettlementTargets(date)
                             → 전표 적재 + 수수료 계산 → 마감
```

- **근거**
  - 인프라가 최소다. 브로커도, 스테이징 테이블도, 파일 저장소도 필요 없음
  - 흐름이 단선적이라 장애 추적이 쉽다 — 실패하면 그 날짜로 재실행하면 끝
  - **유실이 구조적으로 발생하지 않는다.** 이벤트는 "못 받은 걸 모르는" 반면, 배치는 "안 돌았다"가 관측된다
  - 현행 `OrderService.getSettlementCandidates()`를 그대로 살릴 수 있음
  - B안은 **Order가 "정산 대상"을 판단**하게 되어 정산 관심사가 상류로 샌다
- **포기한 것**
  - **경계 규칙 R4 개정** — *"정산은 어떤 상류 서비스도 호출하지 않는 하류 리프"*가 깨진다
    ```
    [개정 R4] 정산은 상류의 공개 API(gRPC)로만 조회하며, 상류 DB에 직접 접근하지 않는다
    ```
    R2(DB 직접 접근 금지)는 그대로 지켜진다. 현행 `SettlementBatchConfig → OrderRepository` 직접 의존을 없앤다는 목표는 변함없음
  - **배치 시각에 Order로 조회 부하가 집중**된다. 대용량에서는 파일/스테이징이 실무 표준이며, 이 결정은 챌린지 규모를 전제로 한다
  - Order 장애 시 정산이 중단된다 (재실행으로 복구 가능)
  - Settlement이 Order의 API 스펙에 결합된다 → ACL 계층에서 번역해 완화
- **구현 제약**
  - 조회는 **반드시 페이징**으로. 단건 응답에 전량을 싣지 않는다
  - Spring Batch 청크 크기와 gRPC 페이지 크기를 맞춰 메모리 사용을 예측 가능하게 둔다
- **재검토 조건**: 배치 시각의 Order 부하가 관측 가능한 수준으로 올라올 때 → C안(파일)으로 전환. 원장 스키마 변경은 불필요
